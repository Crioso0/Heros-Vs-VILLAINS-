# Shipping to phones and desktops

The game is deliberately built so that "make it an app" is a packaging step, not
a port. This document covers three routes, in increasing order of effort:

1. **Install from the browser (done, works today).** The game is a PWA: a phone
   can install it from Safari or Chrome and it runs full-screen and offline.
2. **Desktop via Tauri** — documented below, not built here.
3. **Mobile app-store builds via Capacitor** — documented below, not built here.

**Status:** the web build and the PWA install path are done and tested. The
native shells need a Rust toolchain (desktop) and Xcode/Android Studio (mobile),
which this environment does not have. Nothing in the game code changes for
either.

## Route 1 — install from the browser (PWA)

This is the one that is finished. Everything needed is in the repo:

| Piece | Where |
| --- | --- |
| Web app manifest | `public/manifest.webmanifest` |
| Icons (180/192/512/maskable) | `public/icons/`, generated by `scripts/gen-icons.mjs` |
| Service worker | emitted at build time by the plugin in `vite.config.ts` |
| Registration | `src/main.ts`, production + secure context only |
| iOS meta tags | `index.html` |
| Deploy workflow | `.github/workflows/deploy-pages.yml` |

### Publishing it

`.github/workflows/deploy-pages.yml` builds and deploys on every push to `main`
or a `claude/**` branch. **Two things must be done by hand once**, because the
Pages API cannot be driven by the default workflow token:

1. **The repository must be public** (or the account on GitHub Pro) — Pages does
   not publish private repositories on the free plan.
   Settings → General → Danger Zone → Change repository visibility.
2. **Settings → Pages → Source → "GitHub Actions".** Do this *before* the first
   run, or the deploy job fails with "Get Pages site failed". There is no Save
   button; the dropdown applies immediately.

If you deploy from a branch other than the default, GitHub's auto-created
`github-pages` environment will refuse it with "Branch … is not allowed to
deploy to github-pages due to environment protection rules". Either merge to
`main`, or add a branch rule under Settings → Environments → `github-pages` →
Deployment branches and tags.

The site lands at `https://<user>.github.io/<repo>/` — **with the trailing
slash**, which matters because `vite.config.ts` sets `base: './'` and assets
resolve relative to the document.

### Installing on an iPhone

Open the URL in **Safari** — not Chrome, and not an in-app browser, neither of
which offers Add to Home Screen. Let it load once so the service worker
installs, then Share → Add to Home Screen → Add.

What that gets you: a real icon (not a screenshot of a black canvas), no browser
chrome, no URL bar, and offline play — the whole game is ~130 KB of JavaScript
with no other assets, so the service worker precaches all of it.

### Notes and limits

- **iOS ignores the manifest's `orientation` field.** You cannot lock a
  home-screen web app to landscape on iOS. That is why portrait is a first-class
  layout here rather than an afterthought — see the two profiles in
  `src/render/layout.ts`.
- The manifest deliberately sets `"orientation": "any"`. Android *does* honour
  it, and locking to portrait there would break the landscape layout.
- `start_url`, `scope` and `id` are all `"./"`. Relative manifest members
  resolve against the manifest's own URL, so they are correct under a project
  subpath; `"/"` would break it.
- The service worker is network-first for navigations and cache-first for
  content-hashed assets. `index.html` is the one file Vite does not hash, so
  caching it first would pin a stale build forever.
- iOS evicts unused site storage after about 7 days of no use, which can clear
  saved progress. `navigator.storage.persist()` would mitigate it; not wired up.

## Why it ports cleanly

- **One canvas, one loop.** No DOM UI, no CSS layout, no framework. The entire
  interface is drawn into a single `<canvas>`.
- **Fixed logical resolution.** Everything is authored at 1280×720 and scaled
  and letterboxed to the real window in `src/app/app.ts`. A phone, a tablet and
  a 4K monitor all get the same layout.
- **Pointer events only.** Mouse and touch are normalised into one pointer, so
  touch input already works — no separate mobile input path.
- **No external assets.** Every character, backdrop and sound is generated at
  runtime. The whole build is ~120 KB of JavaScript (~39 KB gzipped) and one
  HTML file. Nothing to bundle, nothing to license, no download on first launch.
- **Relative base path.** `vite.config.ts` sets `base: './'` so the built
  `dist/` is position-independent — it does not assume it is served from the
  root of a domain, which is what both native shells need. Note that the shells
  serve it over a custom scheme (`tauri://localhost`, `capacitor://localhost`)
  or a local HTTP server, *not* a raw `file://` origin: the bundle is an ES
  module, and module scripts are fetched in CORS mode, which `file://` denies.
- **Storage is behind one module.** All persistence goes through
  `src/game/progress.ts`. Swapping `localStorage` for a native file or
  preferences store is a change in that one file.

## Route 2 — Desktop via Tauri

Tauri wraps the built `dist/` in the platform's own webview. The result is a
~5 MB binary rather than the ~100 MB an Electron build would produce, which
matters for a game whose payload is 120 KB.

```bash
npm install -D @tauri-apps/cli
npx tauri init          # answer: dist dir = ../dist, dev url = http://localhost:5173
npm run build
npx tauri build         # produces .exe / .app / .AppImage
```

`src-tauri/tauri.conf.json` wants roughly:

```json
{
  "build": {
    "beforeBuildCommand": "npm run build",
    "beforeDevCommand": "npm run dev",
    "devPath": "http://localhost:5173",
    "distDir": "../dist"
  },
  "tauri": {
    "windows": [{
      "title": "Heroes vs Villains",
      "width": 1280, "height": 720,
      "minWidth": 960, "minHeight": 540,
      "resizable": true, "fullscreen": false
    }],
    "allowlist": { "all": false }
  }
}
```

Keep the allowlist empty — the game needs no filesystem, shell or network
permissions. Add only `fs` scoped to the app data directory if you move saves
off `localStorage`.

**Electron is the fallback** if a Rust toolchain is a problem: same `dist/`,
much larger binary. Do not use `loadFile('dist/index.html')` — that produces a
genuine `file://` origin, which cannot load the ES-module bundle. Register a
custom protocol (`protocol.handle`) or serve `dist/` from a local static server
in the main process, and `loadURL` that instead.

## Route 3 — Mobile app stores via Capacitor

```bash
npm install @capacitor/core @capacitor/cli
npx cap init "Heroes vs Villains" com.example.heroesvsvillains --web-dir=dist
npm run build
npx cap add ios && npx cap add android
npx cap sync
npx cap open android   # or ios
```

`capacitor.config.json`:

```json
{
  "appId": "com.example.heroesvsvillains",
  "appName": "Heroes vs Villains",
  "webDir": "dist",
  "android": { "backgroundColor": "#06070f" },
  "ios": { "contentInset": "always", "backgroundColor": "#06070f" }
}
```

Things already handled in `index.html` that mobile needs: `viewport-fit=cover`
for notches, `user-scalable=no` and `touch-action: none` so the board does not
pan or zoom under a drag, `overscroll-behavior: none` to kill rubber-banding,
and a dark `theme-color`.

Most of what used to be listed here is done — portrait, safe areas, touch
targets and audio unlock all landed with the PWA work. What is left:

1. **Battery.** Consider capping the render loop at 30 fps on mobile. The
   simulation is decoupled at a fixed 60 Hz in `src/net/match.ts` and will not
   change speed, so this only affects how often frames are painted.
2. **Splash screens.** iOS wants a per-device `apple-touch-startup-image` set;
   without them a launched standalone app shows a blank frame briefly.
3. **`navigator.storage.persist()`** against Safari's 7-day storage eviction.
4. **Real-device testing** of the safe-area insets under `black-translucent`,
   which is the one thing a desktop browser cannot faithfully reproduce.

## Performance notes

The heavy costs in a canvas game of this kind are per-frame allocation and
per-frame repaint of static art. Both are already addressed: backdrops are
painted once per world into an offscreen canvas and blitted, the particle layer
is hard-capped, and the simulation runs a fixed number of steps per frame with a
death-spiral guard for slow devices. `FxLayer` and the `reducedFx` setting in
the save data are the levers to pull if a low-end device struggles.
